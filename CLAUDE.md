# CLAUDE.md

This file gives Claude Code project guidance for maintaining this repository.

## Project Overview

Tai Audit Skill is an open-source smart contract audit skill. The repository maintains only `tai-audit`.

Primary runtime: Claude Code. Codex compatibility is supported through the same `SKILL.md` frontmatter and optional `agents/openai.yaml` metadata.

`x-ray` is not vendored here. It is an external companion skill from `https://github.com/pashov/skills`. Tai consumes x-ray outputs from audited projects and can ask the user to install or run upstream x-ray, but this repository must not maintain local `x-ray/` source.

## Install / Update

```bash
./scripts/install.sh
```

Useful variants:

```bash
./scripts/install.sh --with-xray
./scripts/install.sh --target codex --with-xray
./scripts/install.sh --target all --with-xray
X_RAY_REF=v22042026 ./scripts/install.sh --with-xray
```

Default destinations:

- Claude Code: `~/.claude/skills/tai-audit`
- Codex: `~/.codex/skills/tai-audit`

Override with `CLAUDE_SKILLS_DIR` and `CODEX_SKILLS_DIR`.

`scripts/update-claude.sh` is a compatibility wrapper around `scripts/install.sh --target claude`.

## Maintained Skill

### `skills/tai-audit/`

Business-flow-first deep audit skill.

High-level flow:

1. Resolve or generate x-ray context from the audited project.
2. Plan business-flow scope and Tier 0-2 files.
3. Tag selected Solidity source lines by root-cause set.
4. Run Researcher -> Questioner -> Thinker loops across 7 root causes.
5. Consolidate into classified reports under the audited repo's `tai/business/`.

## Repository Rules

- Do not add a top-level `x-ray/` directory.
- Do not reference local bundled x-ray source paths; x-ray is external.
- Keep runtime skill files under `skills/tai-audit/`.
- Put maintainer design notes under `docs/`.
- Use `scripts/check.sh` before declaring structural changes complete.
- Reports generated by Tai belong in the audited project, not this repository.

## Classification Principles

Tai separates vulnerabilities from code facts and trust-model notes:

- `Confirmed Vulnerability`: non-trusted attacker path, reachable entry point, concrete impact.
- `Security Risk`: trusted role, governance, configuration, or external dependency risk.
- `Hardening / QA`: robustness, deployment footgun, dust, best practice, or code quality issue.
- `Research Lead`: plausible but not proven.
- `False Positive`: blocked, unreachable, wrong code fact, or impact does not follow.

Trusted project roles are downgraded unless bypass, forgery, replay, or unauthorized role acquisition is proven.
